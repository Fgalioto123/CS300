Claude:
Good testing practice means deliberately probing the boundaries where bugs like to hide. Here's a rundown of common edge cases to consider when writing Java tests:

## Numeric edge cases
- **Boundaries**: `0`, `-1`, `1`, `Integer.MAX_VALUE`, `Integer.MIN_VALUE`
- **Overflow/underflow**: `Integer.MAX_VALUE + 1` wraps to `Integer.MIN_VALUE`
- **Division**: division by zero (`ArithmeticException` for ints, `Infinity`/`NaN` for doubles)
- **Floating point**: precision issues (`0.1 + 0.2 != 0.3`), `NaN`, `Double.POSITIVE_INFINITY`
- **Negative numbers** where only positive is expected (e.g., array sizes, indices)

## Strings
- `null` vs empty string `""` vs whitespace-only `"   "`
- Very long strings
- Unicode/multi-byte characters, emoji, surrogate pairs
- Special characters (`\n`, `\t`, quotes, escape sequences)
- Case sensitivity assumptions

## Collections & Arrays
- Empty collection/array
- Single-element collection
- `null` collection vs empty collection
- Collection containing `null` elements
- Duplicate elements
- Very large collections (performance/memory)
- Modifying a collection while iterating (`ConcurrentModificationException`)
- Immutable collections (`UnsupportedOperationException` on mutation attempts)

## Object references
- `null` inputs (arguments, return values)
- Same object passed twice (aliasing)
- `equals()`/`hashCode()` contract violations
- Comparing object to `null`, to itself, to a different type

## Control flow / logic
- Off-by-one errors (`<` vs `<=`)
- First and last iteration of a loop
- Recursive base cases (0, negative depth, very deep recursion → `StackOverflowError`)

## Concurrency
- Race conditions
- Deadlocks
- Thread interruption mid-operation
- Shared mutable state accessed by multiple threads

## I/O and external resources
- File not found, empty file, permission denied
- Network timeout, connection refused
- Malformed input (bad JSON, corrupt data)
- Resource cleanup on exception (try-with-resources)

## Exceptions
- Expected exceptions actually thrown (`assertThrows`)
- Exception messages/types matter, not just "something was thrown"
- Checked vs unchecked exception handling
- Resources properly closed even when exceptions occur

## Type-related
- Autoboxing edge cases (`Integer` caching for -128 to 127 means `==` behaves differently outside that range)
- Casting failures (`ClassCastException`)
- Generic type erasure surprises

## Time/date
- Leap years, leap seconds
- Timezone boundaries, DST transitions
- Epoch boundaries (`Instant.MIN`, `Instant.MAX`)

## A few practical tips
- **Parameterized tests** (JUnit 5 `@ParameterizedTest` with `@ValueSource`, `@CsvSource`, or `@MethodSource`) are great for covering many boundary values without duplicating test code.
- **Mutation testing** tools (like PIT) can help reveal edge cases your tests don't actually catch, even if coverage looks high.
- Don't just aim for high line coverage — aim for testing *behavior at boundaries*, since that's where real bugs cluster.
